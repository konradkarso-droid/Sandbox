# Заметки к исполнителю (executor7)

## Неоднозначности контракта и как они решены

1. **Начало счётчика номеров фиксации.** Контракт говорит «растёт на 1» и
   «после восстановления — наибольший n плюс 1», но не говорит, с чего
   начинается. Принято: счётчик — «следующий свободный номер», начало с 0,
   первая фиксация контура 1 — `1-0`. В выгрузке `fixno` — это то же число
   (следующий свободный). Если первая реализация начинает с 1, номера
   разойдутся во всех записях с `fix`.
2. **Субъект записей «создание помощника» и «копия прав помощнику».**
   Субъект — новый помощник `п{i}`, а не порождающий экземпляр (§14).
   Факты записей прежние: помощник назван в них, права копируются из
   таблицы породившего.
3. **Граница памяти (a ≥ 0, b ≥ 0, a + b ≤ длины) для операций 3, 4, 5, 6, 7**
   не проверяется: там `a` — номер (таблицы, ссылки, узла), а `b` не
   используется. Граница проверяется там, где контракт прямо пишет «граница,
   иначе −4»: операции 0, 1, 2, фиксация байтов, сдача ответа.
4. **Память не нужна для** доставки узла, вычисления и выброса узла и для
   отказа «−1 в выход при `--kind 6`»: контракт требует память только для
   фиксации байтов и сдачи ответа (§10.1, п. 1). Для обычных операций
   отсутствие памяти — −4 до проверки номера.
5. **Файлы получателей создаются пустыми при `new`.** Контракт этого не
   требует, но обвязка (`harness.py`, `_project1`) читает `выход1.jsonl` до
   первой доставки. Это замечание к судье, правка в `judge/` не вносилась.
6. **`outside_labels`** в выгрузке — константа `["С"]`, как в контракте.
7. **Что считать неудачной загрузкой.** Ошибка разбора, чужой импорт и
   ошибка создания экземпляра (память больше предела, неверная таблица) —
   «отклонён» с записью «загрузка отклонена». Ловушка исполнения стартовой
   функции — «ловушка» с записью «загрузка: ловушка». Деление определено по
   виду ошибки wasmi (`ErrorKind`). Модуль, у которого начальная память
   больше 2 страниц, попадает в «отклонён»; в контракте этот случай не
   описан.
8. **`main` другой подписи** (с аргументом или результатом) или не функция —
   исход «нет main».
9. **Настройки.** Для `--kind 5б` поля шага 6 — «неизвестное поле»
   (отказ). Значение другого вида, чем у поля по умолчанию (число вместо
   строки и наоборот), — отказ. Сверх контракта отвергаются заведомо
   неработоспособные значения (`levels` вне 1…16, `task_rng` не
   `splitmix`, больше 255 частей задач, пустой документ и т. п.).
9а. **Незавершённые при восстановлении.** Точка «посреди восстановления»
   проходится после первой закрытой записи в каждом контуре, где такие
   записи есть (то есть до двух проходов за восстановление).
10. **Номер запуска при `new`.** Берётся больше наибольшего из счётчика
    процесса и уже существующих папок `run*****` в корне, чтобы новый
    процесс не затёр старые запуски.
11. **Таблицы движка.** Контракт ограничивает число таблиц и памятей, но не
    размер таблицы; задан предел 2²⁰ элементов, чтобы модуль не мог занять
    всю память процесса.

## Различия, которые даёт движок (wasmi)

- Топливо считается единицами wasmi (по одной на инструкцию с поправкой на
  вызовы); число в выгрузке — остаток топлива wasmi. Предел 3 000 000.
- Глубина стека — по умолчанию wasmi (рекурсия 1000 вызовов), ловушка
  «стек исчерпан» — `TrapCode::StackOverflow`.
- Текст причин отказа загрузки — сообщения wasmi.
- Рост памяти сверх 2 страниц даёт −1 через `ResourceLimiter`
  (`memory_size = 131072` на каждую память).
- Стартовая функция и инстанцирование в wasmi 2.0 слиты в один вызов;
  поэтому канарейка записывается сразу после него, а таблица агента
  регистрируется в среде до запуска стартовой функции (ей нужны ворота).

## §15: цена работы среды

- Новые настройки: `gate_price` (0), `check_price` (1, только kind 6). В запись
  «учёт» попадают, только если не по умолчанию; при восстановлении отсутствие
  поля даёт значение по умолчанию (через `Settings::for_journal`).
- Запись «действие» не имеет поля `contour`; её плата относится к контуру по
  последней цифре субъекта (а1, п2). Учёт в `World::apply` — единственное место,
  где плата входит в расход, и онлайн, и при восстановлении.
- Порядок: прежние проверки (−4, −5, −2, −1) → остаток < платы даёт −3 без записи
  → запись с платой → действие. В контракте не сказано, где именно среди прежних
  проверок стоит бюджет для оп 3/4: принято после проверки −5 (переполнение).
- Выброс: проверка «узла нет» (−6) раньше проверки бюджета (−3).
- spawn: плата 2g списывается в `spawn_begin` (отказ −3 учитывается в отказах);
  при неудаче создания `spawn_abort` возвращает её, записи нет. Запись «создание
  помощника» после успеха несёт `charge`; предварительное списание снимается и
  заменяется списанием через запись, чтобы не удвоить.
- При правиле M0 остаток считается бесконечным, поэтому плата за ворота
  отказом −3 не бывает, но записывается и входит в расход.
- `check_price` умножает цену проверки после округления вверх и прежнего
  минимума 1 (min 1 · check_price).
- Итог прогонов: all — 472 запуска, 0 нарушений, 0 расхождений; 5b new — 112/0;
  6 new — 310/0.
- Не сделано: отдельных юнит-тестов на §15 нет, проверка только обвязкой.

## §16: попытка платит

- Настройка `paid_attempts` (0 или 1) разбирается в `settings.rs`; при 1 цены
  `gate_price`, `price`, `fail_price`, `work_price` обязаны быть не меньше 1,
  иначе `new` отказывает. В «учёт» поле попадает, только если оно 1 (так же,
  как поля §15), при восстановлении отсутствие значит 0. При 0 ни один код
  нового правила не пишет в журнал: он идёт за проверкой `cfg.paid`.
- Шаг 0 — `World::attempt_blocked` (gate.rs), общий для `call` и `spawn`.
  Ловушка «бюджет исчерпан» — собственная ошибка хоста `BudgetExhausted`
  (runtime.rs); `trap_kind` даёт для неё текст «бюджет исчерпан», поэтому
  исходы `run` и `load` и запись «загрузка: ловушка» получают его без
  отдельных веток.
- «Отказ ворот» пишет `gate_call` после возврата ворот, если возврат
  отрицательный и попытка не записала свой «отказ». Признак — поле
  `World::own_refusal`, его ставит `refuse` (фиксация, доставка, сдача
  ответа). Для `spawn` то же делает `spawn_begin` (−5 предел экземпляров,
  −3 нет денег на 2g).
- Расход: единственное место учёта по-прежнему `World::apply`; он знает
  `charge` записи «отказ ворот», поэтому восстановление считает его так же.

### Неоднозначности и решения

1. **Стартовая функция помощника.** Решено контрактом §16: остаток ≤ 0 в
   стартовой функции создаваемого помощника не останавливает контур, а
   обрывает создание (ошибка хоста `SpawnAborted` с номером помощника, реестр
   `Contour::starting`, `Halt::AbortSpawn`). `spawn` возвращает −3, плата 2g
   вернулась (`spawn_abort`), записей о создании нет, отказ платит «отказом
   ворот» через `refuse_spawn`. Записи, сделанные стартовой функцией до этого,
   остаются. Ловушка движка в стартовой функции помощника по-прежнему
   обрывает весь вызов, плата возвращается.
2. **Ловушка в `run` после остановки.** Повторный `run` того же агента: любая
   его первая попытка сразу даёт ту же ловушку без записи. Если агент не
   делает попыток, он работает как обычно (правило срабатывает на попытке,
   а не на `run`).
3. **Отказ ворот при −3 без записи (§15).** Остаток к этому моменту больше 0
   (шаг 0), но меньше платы g или 2g, поэтому плата отказа — min(g, остаток),
   а не цена отвергнутого вызова.
4. **Отказ, не написавший отказа, но после записанной «проверки»** (сдача
   ответа: «ответ неверен») — своя запись «отказ» есть, «отказ ворот» не пишется.
   Сдача с −4 (граница памяти) своей записи не имеет и платит как отказ ворот.
5. **Ошибка движка при создании помощника** кончается ловушкой, а не −5 (как
   и до этого захода), поэтому «отказом ворот» не оплачивается.
6. **`check_price`** под правило «все цены ≥ 1» не подпадает: контракт
   перечисляет четыре цены.
7. **M0:** шаг 0 не срабатывает, отказ ворот списывает g, бюджет уходит в минус.

### Неоднозначности и решения

1. **Жизнь процесса модели.** Процесс принадлежит исполнителю, а не запуску:
   `new`, `recover`, `restart` его не перезапускают, убитый остаётся
   мёртвым (шаг 10). Процесс, умерший сам, на шаге 5 ещё жив (§18). Следствие: после `recover` в том же исполнителе
   контур с убитой моделью по-прежнему получает −7.
2. **`recover` при `model` не 0 и без подключённой модели.** Контракт отказывает
   только для `new`. Восстановление разрешено; вопросы тогда получают −7 на шаге 5.
3. **Ответ не по протоколу** (не JSON, нет поля `a`, неверный base64) считается
   «ответа нет»: процесс убивается, пишется «ответ модели» с кодом −7.
4. **Шаг 1 и нет памяти.** Для `модель{i}` другая операция, чем 2, даёт −1 и без
   памяти (как у `узлы{i}`: особый случай стоит раньше проверки памяти, §10.1).
   Оп 2 без памяти — −4 (шаг 1).
5. **Шаг 4 при пустой памяти.** Проверка `a + A > длины` идёт после проверок b
   (шаги 2, 3), как в контракте: b = 0 даёт −6 раньше, чем −4 за ответ.
6. **Метка «М» при пустом ответе.** Ответ длины 0 всё равно добавляет «М»
   (шаг 11 не делает исключения); в память ничего не пишется.
7. **Ответ длиннее A** обрезается по байтам; если обрез рассёк знак UTF-8,
   текст в журнале — `0x…` (правило §10.2), длина — после обрезки.
8. **Отказы шагов 1–6 и «попытка платит».** Своей записи у них нет, поэтому при
   `paid_attempts` = 1 их оплачивает «отказ ворот» (§16). Отказ −7 шага 10 — со
   своей записью, «отказа ворот» после него нет (`own_refusal`).
9. **Плата за байты** считается целочисленным ⌈(b + A) / U⌉ с A — настройкой
   `model_answer`, а не фактической длиной.
10. **Поля `model*` вне `model` = 1.** Проверки `model_answer`, `model_byte_unit`
    идут всегда; нестандартные значения попадают в «учёт» и при `model` = 0
    (контракт: «только если не по умолчанию»).

### Различия, которые дали движок и язык

## §18: режим 2 и способ без сети

- `src/settings.rs`: `model` принимает 0, 1, 2.
- `src/world.rs`: `cfg.model` — «модель включена» (1 или 2), `cfg.model_mode` —
  само значение; `src/gate.rs`: справочник на имя «модель» отдаёт `model_mode`;
  остальные ворота общие для режимов. В «учёт» `"model": 2` попадает как
  любое не умолчательное значение.
- `src/main.rs`: `new` отказывает при `model` не 0 и не подключённой модели;
  параметр `--model-net=netns|probe` (и раздельная запись), другое значение —
  код 2, в том числе без `--model`; без `--model` способ не действует.
- `src/model.rs`: программа из `MODEL_SERVE` запускается сама, не через
  `python3`: при `netns` — `unshare -rn ПРОГРАММА РЕЖИМ…`, при `probe` —
  напрямую, `unshare` не вызывается. Проба — `socket()` библиотеки C (объявлена
  через `extern "C"`, исполнитель собран динамически), четыре сокета, годится
  только `EACCES`/`EPERM` у всех. `alive` больше не вызывает `try_wait`.
- Решения: (а) `recover`/`restart` с `model` = 2 при подключённой модели
  принимаются — исполнитель умеет подключать только модель без сети (оба
  способа её гарантируют), так что отказа по «модель с сетью» нет; (б) при
  `probe` проверка происходит один раз при старте, до запуска процессов, а не
  перед каждым `new`; (в) неверное значение `--model-net` отвергается и без
  `--model` (контракт: «другое значение — исполнитель не запускается»);
  (г) код возврата «не запускается» — 2.
- Ошибок обвязки и наблюдателей не найдено.
- **Процесс модели умирает вместе с исполнителем (§18.1).** `src/model.rs`:
  перед запуском программы модели дочерний процесс (`pre_exec`) вызывает
  `prctl(PR_SET_PDEATHSIG, SIGKILL)` из библиотеки C, затем сверяет `getppid()`
  с запомненным номером исполнителя (родитель мог умереть до просьбы — тогда
  запуск отказывает). Настройка переживает `exec` и `unshare -rn`, поэтому
  действует при `netns` и `probe`. Больше файлов не менялось; журнал и выгрузка
  те же. Неоднозначность: сигнал привязан к потоку-родителю, а не к процессу;
  запуск идёт из главного потока, который живёт до конца исполнителя, —
  решено так, запуск из других потоков не поддержан. Не сделано: на настоящем
  Android не проверялось.
- Не сделано: на настоящем Android проба не проверялась; значения errno
  (13, 1) и констант сокетов — для Linux.

## §14: субъект помощника и права в «начало»

Изменено:
- `src/gate.rs`, `spawn_finish`: субъект записей «создание помощника» и
  «копия прав помощнику» — `п{i}`. Факты, плата (`charge` 2g), порядок
